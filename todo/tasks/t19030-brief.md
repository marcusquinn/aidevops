# t19030: fix(auto-update): make t2119 plist drift detection converge instead of running full setup every 6 hours

## Origin

Interactive session (productivity mission). Found while verifying that the t19026 / GH#38455 `ProcessType=Interactive` launchd change had reached the installed Pulse plist after release v3.39.204. It had not.

## What

The t2119 launchd plist drift check compares a hash recorded by setup with a hash computed by auto-update, but the two sides hash different files, so drift is reported on every check:

- Recorder: `_schedulers_record_template_hash` in `.agents/scripts/setup/modules/schedulers-pulse.sh` hashes `${BASH_SOURCE[0]}`, which has been `schedulers-pulse.sh` since the GH#22419 module split (2026-05-02).
- Checker: `check_launchd_plist_drift` in `.agents/scripts/auto-update-freshness-lib.sh` hashes `setup/modules/schedulers.sh`.

## Why

Observed in the auto-update log: each 6-hourly check from 2026-11-14 02:09 to 2026-11-15 10:10 logged `Plist drift detected: stored='e488ae5b…' current='567d9a9bb578'`. `e488ae5b…` is the hash of `schedulers-pulse.sh` at 11f3517d, and `567d9a9bb578…` is the hash of `schedulers.sh`. Each check ran a full `setup.sh --non-interactive`, and the six runs took 11–23 minutes each, about 100 minutes per day of full deploy plus scheduler I/O on every macOS install. That I/O competes with Pulse workers on already-loaded hosts.

Despite those runs, real scheduler-template changes still do not land promptly:

1. The hash covers one file, while plists are generated by `schedulers.sh`, `schedulers-pulse.sh`, `schedulers-platform.sh`, `schedulers-linux.sh` and `_scheduler_runtime.sh`.
2. The recorder runs inside `setup_supervisor_pulse`, which also runs in pulse-only paths (`--stage pulse`, the incremental planner's `NEEDS_PULSE`). Those paths do not regenerate the watchdog or other plists, so recording there would claim convergence that did not happen.
3. The hash is read when it is recorded, not when setup loaded the modules. A fast-forward during a run can therefore record templates the run never used. Observed: PR #38456 merged at 10:12:18Z during the 10:10–10:22 drift repair, `.deployed-sha` advanced to 6d188ad, and the v3.39.204 incremental update diffed only `6d188ad→1554fee`. The installed Pulse and watchdog plists still lack `ProcessType`, and `launchctl print` reports `spawn type = daemon (3)`.
4. The 6-hour rate limit applies to every check, so even a correct new template hash waits up to 6 hours.

## Tier

tier:standard. Shell-only, bounded to the drift contract, with an existing regression test file.

## How (Approach)

### Files to Modify

- `NEW: .agents/scripts/setup/modules/schedulers-template-hash.sh`: one shared `scheduler_template_hash <modules_dir>` function. It hashes, with stable names, every `schedulers*.sh` in the modules directory plus `../_scheduler_runtime.sh`. This is the same template set the incremental planner already uses at `setup.sh` (`_setup_ai_session_plan_file`).
- `EDIT: .agents/scripts/setup/modules/schedulers.sh`: source the hash module after the sub-libraries and capture `_SCHEDULERS_TEMPLATE_HASH_AT_LOAD`.
- `EDIT: .agents/scripts/setup/modules/schedulers-pulse.sh`: the recorder writes `_SCHEDULERS_TEMPLATE_HASH_AT_LOAD`. Remove its call from `setup_supervisor_pulse`.
- `EDIT: setup.sh`: call `_schedulers_record_template_hash` at the end of `_setup_noninteractive_schedulers` and after the interactive post-setup scheduler list. These are the only paths that regenerate every scheduler.
- `EDIT: .agents/scripts/auto-update-freshness-lib.sh`: `check_launchd_plist_drift` hashes through the shared function from `$INSTALL_DIR`, stays silent when the hashes match, and rate-limits only repeated repair of the same template hash. It records the attempted hash and stamp before starting setup, so a killed run cannot retry every cycle.
- `EDIT: .agents/scripts/tests/test-worker-reliability-self-heal.sh`: update the Part A fixtures to the shared-hash contract and the per-hash rate limit.

### Complete Write Surface

- **Callers/readers:** `run_freshness_checks` (auto-update-freshness-lib.sh) is the only checker. Recorder callers are the `setup.sh` scheduler paths listed above. `.agents/scripts/tests/test-pulse-launchd-setup.sh` stubs the recorder and needs no change.
- **Writers/mutation paths:** `~/.aidevops/.agent-workspace/tmp/schedulers-template-hash.state` (recorder), `plist-drift-check.stamp`, and the new `plist-drift-attempt.state` (checker).
- **Existing verification/tests:** `.agents/scripts/tests/test-worker-reliability-self-heal.sh` Part A; production evidence is the auto-update log line and the installed plist content.
- **Schemas/config:** `AIDEVOPS_PLIST_DRIFT_CHECK_INTERVAL` keeps its meaning for retries of the same template.
- **Generated/deployed mirrors:** deployed via `setup.sh` to `~/.aidevops/agents/scripts/`; plists under `~/Library/LaunchAgents/`.
- **Migrations/backfills:** an old stored hash simply mismatches once, and one repair records the new contract hash.
- **Cleanup/rollback paths:** revert the commit; state files are self-healing.

### Files Scope

## Acceptance Criteria

- [ ] The recorder and the checker produce the same hash for the same checkout, so an unchanged template set never triggers `setup.sh`.

  ```yaml
  verify:
    method: bash
    run: "bash .agents/scripts/tests/test-worker-reliability-self-heal.sh"
  ```

- [ ] Regression guarantee: a changed template hash repairs on the next auto-update cycle even when the 6-hour stamp is fresh, while repeated attempts for the same hash remain rate-limited.

  ```yaml
  verify:
    method: codebase
    pattern: "plist-drift-attempt.state"
    path: ".agents/scripts/auto-update-freshness-lib.sh"
  ```

- [ ] After deployment on macOS, `~/Library/LaunchAgents/com.aidevops.aidevops-supervisor-pulse.plist` contains `ProcessType` `Interactive`, and the auto-update log stops reporting the `e488ae5b`/`567d9a9bb578` drift pair.

## Context & Decisions

- Keep full `setup.sh --non-interactive` as the repair command. Real drift is now rare, and full setup deploys agents before regenerating plists, so new scheduler scripts exist before their plists point at them.
- Record only after a full scheduler pass. Pulse-only paths leave the stored hash stale, so the checker repairs the remaining plists once.
