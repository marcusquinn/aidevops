# t18520: Shared DataForSEO credential resolver for MCP, export and research helpers

## Origin

- **Created:** 2026-09-28
- **Session:** opencode interactive (Build+)
- **Created by:** ai-interactive
- **Parent task:** none (follow-up to t18518/t18519)
- **Conversation context:** `keywords-helper.sh` now resolves DataForSEO credentials from gopass, but the other consumers only source `~/.config/aidevops/credentials.sh`. Operators who store credentials with `aidevops secret set` (the recommended path) get no credentials in those tools.

## What

One shared resolver provides `DATAFORSEO_USERNAME`/`DATAFORSEO_PASSWORD` to every DataForSEO consumer, in this order: environment → `credentials.sh` → gopass `aidevops/DATAFORSEO_API_LOGIN` + `aidevops/DATAFORSEO_API_PASSWORD` → legacy gopass `aidevops/DATAFORSEO_USERNAME` + `aidevops/DATAFORSEO_PASSWORD`. Values are never printed.

## Why

Plaintext `credentials.sh` is the fallback, not the recommended store. Today the DataForSEO MCP server, `seo-export-dataforseo.sh` and `keyword-research-helper-providers.sh` silently lack credentials when they live only in gopass.

### Implementation Steps

1. Create `.agents/scripts/dataforseo-credentials.sh` (sourceable, no side effects at source time, `return 0` everywhere, Bash 3.2 compatible):

```bash
#!/usr/bin/env bash
# Resolve DataForSEO API credentials into DATAFORSEO_USERNAME/DATAFORSEO_PASSWORD.
# Order: environment, credentials.sh, gopass API_* names, legacy gopass names.
# Never prints values.
dataforseo_load_credentials() {
	local credentials="${AIDEVOPS_CREDENTIALS_FILE:-$HOME/.config/aidevops/credentials.sh}"
	# 1-2: environment, then credentials.sh (copy the existing keywords-helper.sh logic)
	# 3: gopass aidevops/DATAFORSEO_API_LOGIN + aidevops/DATAFORSEO_API_PASSWORD (both required)
	# 4: legacy gopass aidevops/DATAFORSEO_USERNAME + aidevops/DATAFORSEO_PASSWORD
	# export both variables only when the username resolved
	return 0
}
```

2. Replace `_kw_load_credentials` body in `keywords-helper.sh` with `source "$SCRIPT_DIR/dataforseo-credentials.sh"` plus `dataforseo_load_credentials`; keep the function name so call sites (lines ~606-611) are unchanged.
3. In `seo-export-dataforseo.sh` and `keyword-research-helper-providers.sh`, source the resolver from their own `SCRIPT_DIR` and call it where `credentials.sh` is sourced today; keep their existing "missing credentials" errors, reworded to recommend `aidevops secret set DATAFORSEO_API_LOGIN` / `DATAFORSEO_API_PASSWORD`.
4. Change the MCP launch command in both `mcp-registry.mjs` and `mcp_config.py` to: `source ~/.aidevops/agents/scripts/dataforseo-credentials.sh && dataforseo_load_credentials && <pkg runner> dataforseo-mcp-server` (the exported variables reach the child process).
5. Update guidance text in `setup-mcp-integrations.sh`, `mcp-setup.sh` and `seo/dataforseo.md`.
6. Run `shellcheck` on every changed shell file, then `bash .agents/scripts/tests/test-keywords-helper.sh`, then the stub-gopass runtime checks below, then `.agents/scripts/linters-local.sh --changed`.

### Hazards and Compatibility

- **Concurrency/atomicity:** read-only lookups; no files or locks are written, so concurrent routines cannot race.
- **Migration/rollback:** order keeps `credentials.sh` ahead of gopass, so existing plaintext setups behave identically; rollback is a revert.
- **Mixed-version/backward compatibility:** until `setup.sh` redeploys, an old OpenCode config still sources `credentials.sh`; the new launch command needs the deployed resolver file, so deploy before regenerating MCP config (setup.sh does both in order). Legacy gopass names remain supported.
- **Idempotency/retry:** calling `dataforseo_load_credentials` twice is a no-op once `DATAFORSEO_USERNAME` is set.
- **Partial failure/recovery:** if gopass is locked or missing, lookups return empty and the consumer shows its existing "credentials not set" error; nothing is half-written.
