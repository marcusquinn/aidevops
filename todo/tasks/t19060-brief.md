# GH transport admission: unbounded `binding` growth pins every host to conservative quota

## Origin

- **Created:** 2026-11-16
- **Created by:** ai-interactive
- **Conversation context:** Interactive DB/pulse health check found `gh_transport_budget.py status` permanently reporting `scope_mode: unresolved` + `stale_multi_credential_scope: true` on a single-GitHub-account host, with REST admission pinned at `remaining: 42 / 5000`.

## What

Make GitHub transport quota attribution converge on a healthy single-account host, so `scope_mode` can become attributed and a later observed reset window can replace a stale low balance instead of pinning REST admission for the remainder of the window.

Two coupled defects must be resolved:

1. `binding` grows without bound and is never pruned, so `credentials_share_proven_owner()` is effectively always `False`.
2. The documented manual escape hatch (`reconcile`) is unreachable, because `AIDEVOPS_GH_QUOTA_OWNER` has no supported configuration surface that reaches every caller.

## Why

Observed on a host with exactly one configured GitHub account (`~/.config/gh/hosts.yml` has a single host entry and a single `user:`):

```text
sqlite3 ~/.aidevops/state/gh-transport/admission.sqlite3 'select scope, count(*) from binding group by scope;'
8295127f...8698|779
```

**779 credential fingerprints are bound to one scope**, while `quota-owners.json` holds only 7 entries (3 share one owner digest, 4 hold `failed_at` timestamps ~34 days old). `credentials_share_proven_owner()` returns `False` as soon as any bound credential lacks an `owner` digest, so with 779 bound rows and 3 proven ones it can never return `True`.

Consequences, all observed live:

- `python3 gh_transport_budget.py status` →
  `{"scope_mode": "unresolved", "ambiguity": "unresolved_scope_has_multiple_credentials", "stale_multi_credential_scope": true, "remaining": 42, "limit": 5000, "reset": 1794813103}`
- `live-windows.json` recorded a **later** reset for the same scope/resource:
  `{"8295127f...8698:core": {"observed": 1794810213.16, "reset": 1794813791}}` — 688 s newer than the stored `reset`, exactly the condition `gh_transport_recovery.py:117` refuses to accept without `one_allowance`.
- Pulse Check reported `queue: queue_budget_exhausted`, `api: {"state": "timed_out", "exit_code": 124}`, and launch blockers `[{"count":2,"reason":"graphql_circuit_breaker"},{"count":2,"reason":"dedup_active_claim_unverified"}]` while GraphQL itself was healthy (`remaining=4380/5000`, `trips_24h=0`).

`reference/github-api-transport.md:155-157` documents the resolution as "owner proof accrues automatically; otherwise reconcile". Neither path works here:

- Automatic accrual cannot catch up: `resolve_owner_proof()` only attributes the credential performing the current read, and `ghs_` installation tokens return `None` unconditionally (`gh_transport_identity.py:61-62`), so retired and app-token bindings never acquire a digest.
- `reconcile` fails closed without a configured owner (`gh_transport_budget_cli.py:28-29` → `{"state": "error", "reason": "set AIDEVOPS_GH_QUOTA_OWNER before reconciliation"}`), and `reference/github-api-transport.md:138-140` requires the owner be set "consistently for every caller". There is no such surface: `~/.config/aidevops/credentials.sh` is sourced only by a handful of domain helpers (`rg -l 'config/aidevops/credentials.sh' .agents/scripts/` does not include the gh transport path), and `~/.config/systemd/user/aidevops-supervisor-pulse.service` is generated by `setup.sh` and would lose a hand-added `Environment=` line on the next deploy.

Net effect: on a normal single-account install the conservative-accounting safety net never releases, so REST progress work is throttled for reasons unrelated to real GitHub capacity.

**Tier rationale:** Requires an unresolved design decision (how bindings expire or are scoped without weakening the GH#33701/GH#33725 cross-credential safety guarantee) plus a SQLite schema change with migration and mixed-version rollout obligations.

### Implementation Steps

1. Reproduce and record the current state with the Worker Quick-Start commands; capture the binding count, `status` JSON and `live-windows.json` reset delta as the before-evidence.
2. Decide the binding lifecycle. Evaluate at least: (a) add `last_seen` to `binding` and have `bound_credentials()` consider only bindings seen inside the current/most recent reset window; (b) prune bindings on write once they exceed an age or row cap; (c) treat permanently unattributable (`ghs_`) bindings as a separate scope rather than an allowance blocker. Record the chosen option and the rejected ones with the safety argument for each.
3. Implement the schema change with an idempotent migration (`PRAGMA table_info(binding)` guard, `ALTER TABLE` when absent) and backfill `last_seen` conservatively for existing rows.
4. Update the binding write path so every governed read refreshes the chosen recency field inside the existing transaction — no extra round trip, no new lock scope.
5. Narrow `bound_credentials()` to the decided set, keeping the conservative default: unknown or mixed owners still never inherit a balance.
6. Add the owner-configuration surface so `reconcile` is actually usable, and make `reference/github-api-transport.md` describe only reachable resolutions.
7. Extend the existing transport tests with the regression: a scope carrying many stale bindings plus one live proven-owner credential must accept a later observed reset window, while a scope with two live credentials holding different owner digests must not.

### Hazards and Compatibility

- **Concurrency/atomicity:** `binding` writes share the admission transaction; the migration must not run inside a path that holds a reservation, and concurrent processes may attempt it simultaneously — make it idempotent and tolerant of `sqlite3.OperationalError` on a losing racer.
- **Migration/rollback:** adding a column is forward-safe; older runtime bundles must keep working against the migrated database. `reference/github-api-transport.md:158-159` already warns that older bundles re-stamp stale resets until they restart.
- **Mixed-version/backward compatibility:** during rollout, an old process writes bindings without the new field. Treat a missing recency value as "unknown", which must stay conservative rather than becoming "fresh".
- **Idempotency/retry:** pruning must never delete a binding that owns a live reservation.
- **Partial failure/recovery:** a failed migration must leave admission usable and conservative, never unbounded.

## Context & Decisions

- Prior art: GH#33701 (stale low core quota for multi-credential unresolved scopes) and GH#33725 (auto owner attribution + the `stale_multi_credential_scope` diagnostic) introduced the current design. This task is the follow-up defect: the diagnostic fires correctly, but neither documented resolution can complete.
- Ruled out: running `reconcile` with a shell-local `AIDEVOPS_GH_QUOTA_OWNER`. The reference doc requires the owner be set consistently for every caller; a one-shell value would reconcile the unresolved scope while pulse and workers kept using the unresolved alias.
- Ruled out: deleting `admission.sqlite3` to clear the bindings. That discards attributed pacing evidence and live cooldown protection, and the table would refill.
- Not a cause: stale runtime bundles. All nine local pulse/worker processes ran bundle `3.39.211`, matching the deployed `~/.aidevops/agents/VERSION`.
